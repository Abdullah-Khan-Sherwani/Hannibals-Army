## Setup
- Tasks / benchmarks (coding? repo-level? research? planning?): Mathematical and competition Olympiad reasoning: MATH-lighteval (12,500 competition problems; 7,500 train, 5,000 test), MATH500, Omni-MATH, MinervaMath, AGI-Eval-MATH, AMC23, and AIME24.
- Models used (per role):
  - Controllers (critic + router): Qwen2.5-7B-Base (System 1), Qwen3-4B-Base (System 2 & Appendix Table 3), Qwen3-8B-Base (Appendix Table 3).
  - Candidate Worker Implementers:
    - System 1: Agent 1 (Strongest): Qwen3-30B-A3B-Instruct; Agent 2 (Medium): Qwen2.5-7B-Instruct; Agent 3 (Weakest): Qwen2.5-1.5B-Instruct.
    - System 2: Agent 1 (Strongest): Qwen3-30B-A3B-Instruct; Agent 2 (Medium): Ministral-3-8B-Instruct-2512; Agent 3 (Weakest): Llama-3-2-1B-Instruct.
- Baselines (single agent? flat team? budget-matched? yes/no + how):
  - Standalone Single Agents: Isolated Agent 1 (30B), Agent 2 (7B/8B), and Agent 3 (1B/1.5B).
  - Standalone Trained Controllers: Controller V1 (controller trained with standard outcome GRPO as standalone solver), Controller V2 (controller trained with paper's method used standalone without agent pool).
  - Router Baselines: Random Router, RoBERTa Router (supervised classifier), RouterDC (dual contrastive embedding router), Router-R1 (NeurIPS 2025 multi-round RL router).
  - Budget-matched / usage-constrained: Yes. Explicit system utilization constraints $\rho_1 = 0.25$ (strongest agent invoked in $\le 25\%$ of total calls), $\rho_2 = 0.50$, $\rho_3 = 1.00$, enforced via Lagrangian multipliers $(\xi_1 = 0.25, \xi_2 = 0.125, \xi_3 = 0.0)$ in the GRPO reward.

## Topology tested
- Depth: 1 (centralized controller coordinating a heterogeneous worker pool).
- Width (workers per orchestrator) and how it was varied: Fixed pool of 3 heterogeneous worker agents spanning small (1B/1.5B), medium (7B/8B), and frontier (30B MoE).
- Roles (planner, implementer, verifier, reviewer, integrator, router, ...):
  - Controller: Dual-role Critic/Verifier and Router. At turn 1, evaluates query difficulty and dispatches to initial agent. At turn $t > 1$, inspects previous agent's solution draft step-by-step, issues a binary verdict (`True`/`False`), and if `False`, re-routes to a strictly stronger agent with critique feedback.
  - Workers (Agents 1, 2, 3): Implementers/solvers generating mathematical solutions conditioned on $(q, g_{t-1}, y_t)$.
- Communication / handoff format; who can write code/files: Text prompt handoffs structured with explicit XML tags. Turn 1 prompt $c$ outputs `<thinking>difficulty rationale</thinking><model>AGENT</model>`. Turn $t > 1$ prompt $c'$ outputs `<checking>step-by-step verification</checking><verdict>True|False</verdict>` and `<model>AGENT</model>` on rejection. Only worker agents produce solution code/proofs; controller only outputs evaluations and routing commands.

## Findings (quote numbers with table/figure/page refs)
- Depth (when does more depth help or hurt?): Multi-turn iterative refinement substantially outperforms one-shot dispatch. In Figure 4 (p. 8), accuracy on MATH-lighteval jumps from 72.8% at Turn 1 to 90.1% at Turn 2 in System 1 (+17.3 percentage points), and from 64.9% to 91.6% in System 2 (+26.7 pp). Performance plateaus at Turn 3 (90.1% in Sys 1, 91.6% in Sys 2), proving a small turn horizon ($T=2\text{--}3$) captures almost all refinement gains.
- Width (where does adding workers plateau?): Tri-tier hierarchy (1B $\to$ 7B/8B $\to$ 30B) allows the system to filter easy problems early. Figure 5 (p. 8) shows only 15.9% of prompts in System 1 and 25.2% in System 2 require the maximum turn budget, meaning 75%–84% of tasks settle in 1 or 2 turns.
- Role → model placement (which tier where, cost vs quality):
  - A compact 4B–7B base model (Qwen2.5-7B or Qwen3-4B) acting as critic-and-router successfully coordinates a 30B frontier model while keeping 30B invocations under 25%.
  - In Table 1 (p. 7), the controller achieves 80.5% average accuracy across 7 benchmarks in System 1 (vs. 85.9% for pure 30B Agent 1), crushing Router-R1 (69.1%, +11.4 pp), RouterDC (57.5%), RoBERTa (61.6%), and Random (56.1%).
  - In System 2 (Table 1), Qwen3-4B controller achieves 82.3% average accuracy (vs. 85.9% for pure 30B Agent 1), beating Router-R1 (66.5%, +15.8 pp).
  - In Appendix Table 3 (p. 14), a Qwen3-8B-Base controller achieves 82.3% average accuracy, outperforming Router-R1 (64.9%) by +17.4 pp.
  - Solutions generated by the strongest model (Agent 1) are accepted without controller re-verification (p. 16, Appendix A.4), eliminating redundant verification compute on frontier outputs.
- Verification / review effects:
  - Tables 6 and 7 (p. 16–17) evaluate controller verification accuracy at Turn 2: the 7B controller in System 1 correctly flags 892 incorrect solutions while falsely rejecting only 216 correct solutions (76.69% incorrect recall, 7.15% false rejection rate).
  - In System 2, the 4B controller detects 1,247 incorrect solutions with only 199 false rejections (80.71% incorrect recall, 7.20% false rejection rate).
  - Table 2 (p. 8) ablations show that training with Lagrangian multipliers $\xi_k$ prevents routing collapse: without Lagrangian penalties, the router routes all tasks to the strongest agent; when evaluated under budget constraints, unconstrained models collapse to 56.5% (Sys 1) and 50.1% (Sys 2), while Lagrangian-trained models achieve 80.5% and 82.3%.
- Cost / tokens / latency: Strongest agent usage is kept below $\rho_1 = 0.25$ (Figure 3c & 3f, p. 8). System 1 reaches 93.7% of frontier agent accuracy (80.5% / 85.9%) and System 2 reaches 95.8% (82.3% / 85.9%) while calling the 30B model on fewer than a quarter of requests.
- Failure modes observed:
  - One-shot routing difficulty bias: Confusion matrices in Tables 4 & 5 (p. 15) show one-shot routers severely under-route hard problems to weak models when uncertain (e.g. 515 medium and 211 hard problems routed to 1.5B agent in System 1).
  - False acceptance: 271 incorrect drafts in System 1 and 298 in System 2 passed controller verification unchecked (Tables 6 & 7).
  - Turn budget exhaustion on Olympiad-grade problems (Omni-MATH, AIME24).

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: INFERENCE: A Depth-1 coordinator must perform sequential evaluation (critique + routing) rather than one-shot pre-routing, because pre-execution difficulty estimation is inherently noisy and biased toward under-routing hard tasks.
- Depth-2 design: INFERENCE: Sub-orchestrators should execute local verify-and-reroute loops (escalating tasks from cheap implementers to mid/frontier implementers upon failure) before reporting back to the top coordinator, preventing unnecessary frontier escalations across the cluster.
- Which agent/model type goes in which seat:
  - Orchestrator / Verifier Seat: INFERENCE: Compact, reasoning-optimized models (e.g. 4B–8B parameter class) are sufficient to act as verification controllers, achieving 77%–81% incorrect-draft detection recall while preserving $>92\%$ true acceptance.
  - Implementer Seat: INFERENCE: Implementers should follow a tiered waterfall: cheap/fast models handle initial drafts (filtering easy/medium tasks), while frontier models are reserved for verified-failed escalations (capped at $<25\%$ invocation share).
  - Frontier Model Verification Bypass: INFERENCE: When a task is escalated to and implemented by the top-tier frontier model, skip subsequent verifier re-checks to conserve inference budget.

## Validity
- Evidence grade: B = preprint + controlled (arXiv May 2026, rigorous controlled ablations across 7 benchmarks, 2 heterogeneous systems, 4 controller architectures).
- Threats (contamination, not budget-matched, toy tasks, single model family, ...):
  - Benchmarks are pure mathematical problem solving; code patch editing with execution environments may alter critique dynamics.
  - Closed agent pools of size 3 (1B, 7B/8B, 30B); does not evaluate arbitrary large dynamic tool suites.
  - Verification is rule-verifiable on math answers during training; open-domain software engineering requires LLM-as-judge or test harness integration.
