## Setup
- Tasks / benchmarks (coding? repo-level? research? planning?): Repo-level coding review — SWE-Review-Bench: 1,384 AI-generated candidate PRs over 500 SWE-bench Verified issues; three PR generators spanning quality tiers (GLM-5 72.2% resolve, Qwen3-Coder-30B-A3B 50.9%, Qwen3-30B-A3B 27.5%). Review trajectories from SWE-rebench issues (no benchmark-repo leakage); SWE-Review-Traj = 8,914 decision-correct agentic review trajectories.
- Models used (per role): Frontier reviewer = Claude Opus 4.6 (fixed in main comparisons); reviewer-to-be-distilled = Qwen3-8B / Qwen3-30B-A3B via SFT; teacher for trajectory collection = open-weight GLM-5 with thinking; PR generators = GLM-5, Qwen3-Coder-30B-A3B, Qwen3-30B-A3B; judge models for diagnosis validation = Opus 4.6 and GPT-5.4; scaffold OpenHands-SDK for both generators and reviewers.
- Baselines (single agent? flat team? budget-matched? yes/no + how): No-review baseline (keep PR as-is); single-turn review baselines (diff-only and diff+retrieved-context, same reviewer model); verifier-selected best-of-N with SWE-Lego-Verifier-8B; reviewer-gated resampling. Comparisons hold reviewer/verifier size matched (8B vs 8B) in test-time scaling and share the same generators — controlled within-paper, not budget-matched on $.

## Topology tested
- Depth: 1 — a single reviewer agent sits between generator and merge in a generate-review-revise loop (reviewer → decision + diagnosis; diagnosis goes back to the generator for revision). No sub-orchestrators.
- Width (workers per orchestrator) and how it was varied: Not varied for reviewers (1 reviewer per PR). Sample-width varied in test-time scaling: max sampling budget K ∈ {1..16} (Fig 5, p.9).
- Roles (planner, implementer, verifier, reviewer, integrator, router, ...): Generator (coder) → Reviewer (repository-grounded decision + structured diagnosis: defects, locations, suggested fixes) → Revision by generator. The reviewer can run commands/tests in the environment, browse files, grep, execute reproducers.
- Communication / handoff format; who can write code/files: Review report = binary approve/request-changes + structured diagnosis (Defect/Location/Description/Suggested Fix, Fig 1). Approved PRs are kept unchanged; request-changes PRs go back to the original generator with feedback for exactly one revision in the RRR protocol (§3.1, p.4). Reviewer writes tests into a sandbox (e.g., reproduce_bug.py in Fig 2); only the generator writes the patch.

## Findings (quote numbers with table/figure/page refs)
- Depth: Single reviewer in the loop transforms weak generators: resolve rate 27.5%→52.6% (Qwen3-30B-A3B, +25.1), 50.9%→67.3% (Qwen3-Coder-30B, +16.4), 72.2%→75.2% (GLM-5, +3.0) (Fig 1, p.2; Table 2, p.8). The marginal value shrinks as generator quality rises.
- Width: Review-guided iterative revision with budget K=5 and only 2.44 samples used on average reaches 38.4% resolve (from 22.9% baseline), while verifier best-of-16 (full 16 samples) reaches only 25.6% and reviewer-gated resampling 32.3% at 8.86 samples avg (Fig 5 + Table 14, pp.9,19).
- Role → model placement: Frontier reviewer (Opus 4.6) beats both single-turn variants on every generator split: DA 75.6/80.5/89.4 vs best single-turn 69.8/73.8/82.7, RRR 75.2/67.3/52.6 vs 72.6/57.6/44.1 (Fig 3, p.5). But reviewer strength must match generator strength: distilled SWE-Review-8B provides "no RRR gain ... when reviewing GLM-5 patches" (72.2 no-review vs 71.6, -0.6) yet +7.6 on weak-gen patches; "clear gains on GLM-5 patches emerge only when the reviewer is strong enough" (§4.2, p.7; Table 2, p.8). Reviewer efficiency: GLM-5 reviewer 77.3% DA at 1,302K tokens (1,685K tokens/correct decision) vs SWE-Review-30B 72.0% at 2,297K (3,190K/correct) vs 8B 69.1% at 2,366K (3,423K/correct) (Table 13, p.19).
- Verification / review effects: Agentic (repository-exploring) review beats fixed-context review, and the gap widens monotonically with difficulty: DA hard tertile 76.5 vs 68.1; RRR hard 52.2 vs 40.8 (Fig 4, p.5). Diagnosis carries actionable information beyond a binary verdict: RRR with no review 3.0%, decision-only 8.0%, teacher diagnosis 21.0%, oracle diagnosis 32.0% (Table 1b, p.7) — i.e., the diagnosis recovers ~2/3 of the gap to the oracle. Reproducer execution is the strongest behavioral predictor of decision accuracy: Opus runs reproducers in 99.9% of trials vs 76.7% (8B); Opus reads only 1.3 files on average (63% stays in the diff region) yet has highest DA — "exploration efficiency, rather than volume, predicts review quality" (Table 5, p.16).
- Cost / tokens / latency: Review is a fixed-cost understanding phase: review consumes 2.19M–2.46M tokens regardless of generator quality; its budget share rises from 35.6% (strong generator) to 65.9% (weak generator) (Table 11, p.19). Error cases burn more: Opus incorrect decisions +33% tokens (186K vs 140K); fastest step-quartile (≤17 steps) 90.8% DA vs slowest (>28 steps) 69.4% (OR 4.32, p<0.001) → step count as a confidence proxy (pp.15-16).
- Failure modes observed: Opus made 272 DA errors (167 false approvals, 105 false rejections; Table 8, p.17). False approvals dominate against strong generators (20.2% FA rate on GLM-5 patches); false rejections dominate against weak generators (Qwen3-30B split: 57% of errors FR). FA root causes: subtle logic bugs 37.7%, insufficient reproducer coverage 32.1%, cross-file reasoning gaps 29.0%; FR root causes: misread code 44.3%, "non-standard but correct" solutions 25.8% (Table 9, p.18). The "test paradox": 82% of FA review reports contain the keyword "pass" — reviewer-written tests gave false confidence; 62% of falsely approved patches include test files written by the same AI that generated the patch (self-confirming tests); in FR reports 42% contain "fail" where reviewer blamed the patch for its own faulty test (p.18). Nearly half of FAs (80) are in the hard tertile (Table 10, p.18).

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: (INFERENCE) The reviewer seat is the army's highest-leverage single addition: one repo-grounded reviewer with execute access raised a weak generator from 27.5% to 52.6% resolve. The user's "independent read-only reviewers audit diffs" is validated, but should be upgraded: reviewers must be able to run reproducers/commands in a sandbox (read-only on code, executable), because reproducer execution is the strongest predictor of accurate review.
- Depth-2 design: (INFERENCE) Full strength on review scales with model tier — sub-orchestrators reviewing sub-team output should be at least as capable as the workers they gate; a cheap 8B/Flash reviewer over strong-model patches adds nothing (SWE-Review-8B on GLM-5: -0.6 pts). Hannibal's Army rule "generals are Sonnet-class and review; Flash implements" fits: don't let the same cheap tier review its own output.
- Which agent/model type goes in which seat: (INFERENCE) Reviewer = the strongest available model when gating strong-model patches (Opus-class or Sol); implementer/reviser can be cheap; verifier-by-execution (tests) is cheap and should be automatic and independent of the implementer. Apply "hard instances get deeper review" (FAs concentrate in hard tertile).
- Anti-patterns to institutionalize: (INFERENCE) (1) Tests written by the same agent that wrote the patch give false confidence (62% of false approvals) — the Army's rule that verifiers write independent tests is justified; audit cases where "review" consists only of the author's own tests passing. (2) Long review trajectories signal uncertainty (slowest quartile DA 69.4%): treat blow-up of a reviewer's turn count as a trigger for a stronger model or human escalation. (3) Step/round counts are a usable cheap confidence signal for the ack/heartbeat discipline.

## Validity
- Evidence grade: B (preprint, but strongly controlled: fixed reviewer model across all comparisons, three generator tiers, executable ground truth for DA/RRR, ablations incl. oracle upper bound; single scaffold OpenHands-SDK; no monetary budgets, tokens reported).
- Threats (contamination, not budget-matched, toy tasks, single model family, ...): Review scope limited to SWE-style bash/Python issue resolution (Limitations, p.9); metrics are functional only (no security/style/maintainability) — my lane's security-review angle is untested here; DA/RRR depend on a single revision round for RRR; the strongest reviewer (Opus 4.6) reasoning tokens are unmeasured, so cost comparisons understate frontier reviewer cost; results are from the authors' own benchmark (self-built), though built on public SWE-bench Verified issues; SFT-distilled reviewers are Qwen-family; teacher GLM-5 used for trajectories may bias diagnosis style. Paper is v1 preprint — numbers may change.
