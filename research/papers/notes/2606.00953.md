## Setup
- Tasks / benchmarks (coding? repo-level? research? planning?): Repo-level code generation from spec — DevEval Python subset (10 projects; ground truth avg 3.1 files / 243 LOC) and CodeProjectEval (18 real-world projects; avg 11.9 files / 2,371 LOC). 28 tasks; three independent runs per repository; unit-test pass rate as correctness.
- Models used (per role): All methods use gpt-5-mini (single model for every role — no routing study). Sequential / File-based / Co-Coder run on OpenHands SDK v1.11.4; Claude Code w/ Agent Teams at v2.1.119 via LiteLLM proxy as external reference.
- Baselines (single agent? flat team? budget-matched? yes/no + how): (a) Sequential single agent (owns whole repo); (b) File-based Parallel (one agent per file, concurrent, free-form communication, no partitioning/scheduling); (c) Claude Code with Agent Teams (commercial agent-team mode); all receive identical input specs / shared Repository Interface Blueprint and the same base model — controlled and cost-measured (latency + API $).

## Topology tested
- Depth: 1 — one orchestrator (leader) that partitions and schedules; workers are per-group coding agents. No sub-orchestrators. It is an intentional contrast to self-organized (leaderless) teams: Claude Code Agent Teams "message each other directly" while Co-Coder institutes explicit partition-then-schedule.
- Width (workers per orchestrator) and how it was varied: Worker count = number of cohesive groups, determined by the partition algorithm (not a swept hyperparameter; K emerges from Infomap + hub isolation + lifting). The paper's formalization covers arbitrary K with a communication-vs-critical-path objective T(P) = W(P) + α·C(P) (Eqs. 1-3, §2).
- Roles (planner, implementer, verifier, reviewer, integrator, router, ...): Orchestrator: builds RIB, partitions, schedules via shared task list (pending→ready→running→done), then runs tests and dispatches failures to the owning group's agent ("leader agent runs the project's test suite and uses the partition record to localize each test failure to the group that owns the responsible file", §3.3). Workers: per-group file generation + targeted repair. No dedicated reviewer/verifier seat; the test suite + partition record play the verifier role.
- Communication / handoff format; who can write code/files: Explicit "Repository Interface Blueprint" (RIB): LLM-generated file-level symbol/import skeleton with class names, function signatures, typed parameters, constants — acts as the shared interface contract; both graph construction and (fairness) baselines use it. Cross-agent dependencies resolved via dependency-aware list scheduling rather than peer messaging: downstream files are generated only after upstream files complete, so workers read actual interfaces "rather than speculative placeholders" (§6, p.8). Hub files: "in-hubs" (widely-depended utilities) are singleton-isolated; "out-hubs" (top-level aggregators) are gathered into one integration group (§3.2).

## Findings (quote numbers with table/figure/page refs)
- Depth: Naive parallelism fails; structured parallelism wins. File-based Parallel (one agent per file): DevEval +0.9 pts pass rate for +44% cost and no latency gain (806s vs 800s); CodeProjectEval +3.2 pts for +60% cost (Table 1/2; §5). Claude Code w/ Agent Teams: fastest on CodeProjectEval (680s = 0.25×) and cheap ($0.38 = 0.37×) but LOWEST pass rate (16.3%), below the sequential single agent (20.1%) (Table 2, p.7). Co-Coder improves all three simultaneously: DevEval 68.1% pass (+11.3 pts over 56.8%), 0.55× latency, 0.72× cost; CodeProjectEval 34.1% (+14.0 pts over 20.1%), 0.48× latency, 0.65× cost (§5, pp.6-7).
- Width: Not swept; instead the partition granularity knob (Markov time of Infomap) trades communication cost C(P) against serialization W(P) (§3.2). Limitation: near-complete coupling collapses the partition to a single group and execution degrades to sequential (Limitations, p.9).
- Role → model placement: Not tested (single model gpt-5-mini everywhere). The paper's placement claim is structural, not model-based: partition-owner agents and one test-dispatching leader suffice.
- Verification / review effects: Repair loop is partition-scoped: "repair requests can be dispatched partition-by-partition rather than broadcast to the whole system: each agent reasons over a bounded slice of context, and conflicting edits across groups are avoided by construction" (§3.3, p.6; fixed number of rounds, re-running tests and re-dispatching only groups with failing files). No reviewer ablation; correct interfaces come from RIB + topological scheduling, correctness from suite + targeted repair.
- Cost / tokens / latency: Headline numbers above (per-project tables 1-2). Cost/latency normalized to Sequential: File-based 1.01× time / 1.44× cost on DevEval; Claude teams 0.25× time / 0.37× cost but quality loss; Co-Coder 0.55×/0.72× and 0.48×/0.65× on the two benchmarks.
- Failure modes observed: Concurrent independent file generation "frequently violate[s] cross-file type contracts, leading to expensive yet unproductive iterations" (§5, p.8). Interface mismatch growth is superlinear in coupling: a file importing symbols from k files creates k mismatch points; edge density (|E|/|V|) correlates with Co-Coder's pass improvement over Sequential: Pearson r=0.65, Spearman ρ=0.60 (both p<0.05, 16 CodeProjectEval projects with non-zero pass rates) (§6, p.8). Claude teams sacrifice quality for speed; sequential keeps interfaces consistent but wastes parallelism; Co-Coder's gains are largest on dependency-dense projects (e.g., simpy 58.0/149 vs 10.3; pyjwt 140/294 vs 79; cookiecutter 74.7/375 vs 59) (Table 2, p.7).

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: (INFERENCE) The user's "disjoint worktrees/file ownership + one merge" rule is the right shape, but this paper quantifies the missing piece: assign workers by *cohesion* (tightly coupled files/modules together in one worker's scope), not mechanically per-file. Per-file fan-out is empirically the worst configuration on dependency-dense repos (+cost, no speed, tiny quality gain) — supports the user's instinct to keep fan-out minimal and give each soldier a coherent bounded module.
- Depth-2 design: (INFERENCE) Sub-orchestrators' scopes should be cut along the same community structure: in-hub-like shared utilities should be owned by the "steward" seat (single writer), and out-hub top-level integration should live with the integrator. Dependency-aware scheduling (release downstream tasks when upstream done, no global barriers) is the concrete mechanism for the Army's staged hand-offs; a shared interface contract file (RIB-analogue) should be produced in the design phase and be inputs to every worker spec.
- Which agent/model type goes in which seat: (INFERENCE) No model routing evidence here; the transferable seat guidance is (a) verifier = test suite + failure-to-owner localization via the partition record (cheap and exact), (b) one leader/integrator agent that owns scheduling and scoped repair dispatch — matching "sole integrator" and "steward" seats.
- Anti-pattern confirmed: (INFERENCE) Self-organized teams that message each other directly (Claude Code Agent Teams here) bought speed at the cost of correctness; for the user's "don't hand-hold / minimal chatter" design, this argues for central partition + contract rather than peer-to-peer negotiation between workers.

## Validity
- Evidence grade: B+ (preprint; controlled: identical base model and input specs across all four methods, three runs/repo, cost and latency measured, external commercial baseline; modest task count and one language).
- Threats (contamination, not budget-matched, toy tasks, single model family, ...): Single base model (gpt-5-mini); DevEval projects are small (avg 3 files) where differences mostly vanish; CodeProjectEval (18 projects) carries the headline result — sample size limits the correlation analysis (16 usable projects); Python-only (authors flag static-typed languages as untested); decomposition relies on an LLM-generated RIB whose quality is not ablated; commercial baseline (Claude Code teams) may not be run at its best configuration; pass-rate metric is test-suite dependent (some projects 0% for all methods, e.g., flask/portalocker — heavy tasks where every system fails).
