## Setup
- Tasks / benchmarks (coding? repo-level? research? planning?): Repo-level coding with explicit cross-agent dependencies — 19 tasks from 16 real repositories (framework/library, systems/storage, compiler/IR, network protocols, security), 64 implementation units, 52 human-validated directed dependency edges (3 reviewers validate each edge/direction with executable evidence; graphs frozen before evaluation). Tasks packaged with fixed revision, answer-free instruction, scoped writable paths, pytest evaluator, task-specific Docker + OpenHands harness.
- Models used (per role): 10 open-weight models spanning 9B dense to 284B MoE: Qwen3.5-9B/27B, Qwen3.6-27B, Qwen3.8-27B, Qwen3-Coder-Next (80B/3B active), DeepSeek-V4-Flash (284B/13B active), Gemma-4-26B (MoE), Muse-Glimmer-30B, GLM-4.7-Flash, Nemotron-3.5-Lightning. Same model fills specialist and manager seats per condition (no cross-model routing tested).
- Baselines (single agent? flat team? budget-matched? yes/no + how): Single-agent full-task baseline (SINGLE) vs 4 multi-agent protocols with identical task package/harness/evaluator and identical specialist roles/writable scopes; token costs measured per protocol (Pareto analysis, RQ4). Fixed model configuration across protocols = controlled.

## Topology tested
- Depth: 1 — orchestrator–worker only. ASYNC-MANAGER-RO and ASYNC-MANAGER add a single manager over concurrent specialists (no sub-orchestrators). Explicit acknowledgement that manager-centric design follows "the orchestrator–worker pattern used in prior multi-agent systems."
- Width (workers per orchestrator) and how it was varied: specialists per task are manifest-defined (varying by task, not swept); protocols vary concurrency (serial vs concurrent private worktrees) rather than count.
- Roles (planner, implementer, verifier, reviewer, integrator, router, ...): Manager (RO: inspect, plan, feedback, request scoped follow-ups, coordinate integration — cannot modify production code; full: may submit scoped production patches from its own private worktree, policy-checked) + specialists (scope-validated artifacts, deterministic dependency-order integration). Dependency Checkers act as verifiers (upstream/downstream/integrated groups).
- Communication / handoff format; who can write code/files: Specialists write only within manifest-scoped paths; artifacts scope-validated before integration; deterministic merge order; integrated-workspace checkpoints after each integration/manager intervention; ADPR/DRS computed over checkpoints. Manager never edits integrated workspace or specialist worktrees directly.

## Findings (quote numbers with table/figure/page refs)
- Depth: Multi-agent is not uniformly better: 6/10 models improve under their best multi-agent protocol (+7.8% to +22.7% Test Pass Rate), 4/10 are worse even at best protocol; the strongest single-agent models regress under decomposition (Qwen3.8-27B 93.6% SINGLE → 86.7% best multi; DeepSeek-V4 93.6% → 89.9%) (Fig 2a, §5.2, p.6). Manager WITH bounded repair (ASYNC-MANAGER) is the strongest collaboration configuration in most model rows of Fig 4a (e.g., Qwen3.6-27B +26.3% ADPR vs single; Gemma-4-26B +19.1%; Qwen3.5-27B +19.3%), while pure async concurrency without a manager (ASYNC-PRIVATE) is usually negative (Qwen3.6-27B: -14.9%; DeepSeek-V4: -33.3%).
- Width: Not swept; the benchmark instead shows coordination outcome depends on protocol × model with 41.2% ADPR spread for one model (Qwen3.6-27B ranges -14.9% under ASYNC-PRIVATE to +26.3% under ASYNC-MANAGER) and "no collaborative protocol consistently improves dependency resolution across all models" (§5.4, p.8).
- Role → model placement: Manager seat tested with the same model as workers (no routing study). Model capability findings: scaling Qwen3.5 9B→27B raises Test Pass Rate everywhere (24.4→42.1 SINGLE; 36.9→59.2 ASYNC-MANAGER) but ADPR gains are protocol-dependent (ASYNC-MANAGER 2.8→31.6; SINGLE 14.2→12.3). Generational improvement at 27B: SINGLE TestPass 42.1→57.4→93.6 (3.5→3.6→3.8), ADPR 12.3→36.8→77.2; but ASYNC-MANAGER ADPR plateaus (31.6→63.2→64.9) — standalone gains stop transferring to collaboration (§5.3, pp.6-7).
- Verification / review effects: ADPR exposes hidden coordination failures that task-level tests miss: across 190 ASYNC-MANAGER-RO model-task outcomes, Test Pass Rate and ADPR correlate only r=0.617/ρ=0.613; Test Pass Rate exceeds ADPR in 136/190 (71.6%) outcomes (mean 48.0% vs 18.8%); 32 outcomes show ≥80% Test Pass Rate with <half dependencies resolved, including 26 with ZERO ADPR; no low-test/high-ADPR cases (Fig 2b, §5.2, p.6). I.e., a green test suite can hide that cross-agent interfaces are broken.
- Cost / tokens / latency: Token costs per protocol measured; quality–cost Pareto frontiers depend on the quality metric: for Nemotron-3.5, ASYNC-PRIVATE raises Test Pass 28.99→32.94% at higher tokens but with unchanged ADPR (1.05%), while ASYNC-MANAGER-RO reaches ADPR 2.81% but is dominated by ASYNC-PRIVATE under Test Pass Rate; 5/10 models have different within-model Pareto frontiers under the two metrics (Fig 6, §5.5, p.9).
- Failure modes observed: (1) "Hopping window": dependency closures are not gradual — 34.9-67.8% of eventual closure mass lands in 0.50<x≤0.75 of normalized execution (28/40 model-protocol configurations; ALL 16 configurations that reach ≥20% final ADPR show it; flat trajectories ⇒ little closure) (Fig 4b/5, §5.4, p.8); (2) models can reach similar final ADPR via different trajectories (Qwen3.6 DRS 0.641 vs Qwen3.8 0.719 despite similar final ADPR under ASYNC-MANAGER); (3) stale-dependency failures from async private work (downstream built against outdated upstream; Fig 1) — invisible to outcome-only evaluation; (4) stronger standalone coding ≠ stronger collaboration.

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: (INFERENCE) Direct evidence for the field-marshal shape on parallel workers: (a) a coordination layer that can also do bounded repair beats both pure parallelism and read-only management (ASYNC-MANAGER ≥ others for ADPR in most model rows) — so the user's "sole integrator" and general-level review/repair should have bounded write access, not just advisory role; (b) concurrent private worktrees without a manager are the worst configuration when dependencies exist — matches the user's rule that parallel workers must have disjoint files and an explicit merge step. Also: the acceptance test for a sub-team should include cross-worker interface checks (the user's integrator should assert "downstream uses the new interface"), not just per-worker tests, because 26/190 runs had zero dependencies resolved behind ≥80% green tests.
- Depth-2 design: (INFERENCE) Sub-orchestrators add another dependency boundary (their workers' outputs must compose with sibling sub-teams' outputs); the hopping phenomenon suggests checking cross-boundary dependencies late in the run (≈50-75% through) is when closure actually happens — schedule an explicit integration checkpoint then, not only at the end.
- Which agent/model type goes in which seat: (INFERENCE) The manager/coordinator can be a weaker or same-tier model in this benchmark, but only if it has real integration authority (bounded repair) — a read-only manager mostly reorders tokens. Combined with SWE-Review (reviewer strength must scale with worker strength), the pattern for the Army: cheap workers OK under strong integrator/reviewer; document interfaces as dependencies and verify them at integration.
- Metric design: (INFERENCE) Track ADPR-like dependency checks per handoff (does file B consume the new interface from file A?) in the findings ledger; use token-vs-ADPR Pareto when deciding whether a fan-out paid off (Test Pass Rate alone can make wasteful fan-outs look good).

## Validity
- Evidence grade: B (preprint; benchmark with independent human validation of dependencies, frozen graphs, identical packages/harness/evaluator across protocols, token accounting; but small task count).
- Threats (contamination, not budget-matched, toy tasks, single model family, ...): Only 19 tasks/52 dependencies — aggregate percentages rest on modest samples; only open-weight models (no frontier API models like GPT-5/Claude Opus); single scaffold (OpenHands), Python repos with pytest; manager and workers share one model per condition, so "manager capability" findings are model-family-wide, not role-specific; the ASYNC-MANAGER's bounded repair changes the amount of writing, so part of its advantage may be extra compute rather than coordination per se; DRS is defined on logical checkpoints (not wall-clock), so timing findings are protocol-relative.
