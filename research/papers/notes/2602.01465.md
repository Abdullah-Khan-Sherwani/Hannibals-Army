## Setup
- Tasks / benchmarks (coding? repo-level? research? planning?): Repo-level coding — SWE-bench 500, text-only subset ("SWE-bench 500 setting [Jimenez et al., 2024]", p.7). Real production system from day-to-day engineering use, evaluated post hoc; explicitly NOT tuned for SWE-bench (abstract; §1).
- Models used (per role): manager + researcher = GPT-5 (medium reasoning, "larger general-purpose models, stronger reasoning and broader context"); engineer + reviewer = GPT-5-Codex (medium reasoning, code-specialized) (§3.1 p.5; §4.1 p.7). Fixed configuration across all tasks.
- Baselines (single agent? flat team? budget-matched? yes/no + how): Comparison restricted to GPT-5-family systems (Table 1, p.7): OpenHands+GPT-5 71.8%, mini-SWE-agent+GPT-5.2 (high) 71.8%, mini-SWE-agent+GPT-5 (medium) 65.0% vs agyn 72.2%. Baseline is mini-SWE-agent; claimed +7.4% over "the baseline mini-SWE-agent under comparable model configurations" (contributions list p.3, computed vs 65.0% GPT-5 medium, though reviewer uses GPT-5-Codex). Not fully budget-matched — no cost/token table; comparison is same model family, not same spend.

## Topology tested
- Depth: 1 — one manager agent (orchestrator) → three worker agents (researcher, engineer, reviewer); manager is the single coordination point ("All inter-agent communication flows through the manager", §3.3 p.5-6). Manager does not implement ("Rather than executing work directly", §3.1 p.5). No sub-orchestrators (depth-2 untested).
- Width (workers per orchestrator) and how it was varied: fixed 3 workers (researcher + engineer + reviewer); not varied. Number of interaction steps / review iterations is dynamic, not fixed pipeline (§2 positioning p.4, §3.3).
- Roles (planner, implementer, verifier, reviewer, integrator, router, ...): manager (coordination/planning/state), researcher (issue understanding, repo exploration, task specification), engineer (implementation, tests), reviewer (verifies diff, inline PR review, approve-or-request-changes). Reviewer approval is the system-level termination condition; reviewer can request changes → iterative loops (§3.1 p.5, §3.6 p.6-7).
- Communication / handoff format; who can write code/files: hub-and-spoke via a `manage` tool (manager invokes agents with task context, collects outputs); no agent-to-agent direct messages. GitHub-native artifacts as persistent shared state: separate GitHub account per role, issues, forked repos + base branch, pull requests with task ID in title, inline PR review comments (requires custom `gh-pr-review` extension; MCP/GitHub API was too verbose and degraded review workflows, §3.4 p.6). Each agent has its own isolated sandbox (own environment, Nix package manager, can install deps; no predefined tools beyond git/gh). Only the engineer appears to write code; reviewer only reviews; manager coordinates; researcher reads/specs.

## Findings (quote numbers with table/figure/page refs)
- Depth: n/a (depth held at 1). Qualitative claim that manager-coordinated workflow beats both single agent and fixed pipelines within GPT-5 family (72.2 vs 71.8 / 71.8 / 65.0, Table 1 p.7); differences small, authors caution "Small numerical differences on the leaderboard should therefore be interpreted with caution" (§4.4 p.7).
- Width: not varied; fixed at 3 workers. Parallel execution mentioned only as infra stress (multiple tasks in parallel on one MacBook caused OOM, §5.2 p.9).
- Role → model placement: reasoning-heavy manager + researcher → GPT-5; implementation/review → GPT-5-Codex (smaller, code-specialized). Authors frame this as production cost/quality balancing: "Different stages ... impose different requirements on context size, reasoning depth, tooling, and model capabilities" (§1 p.2; §3.1 p.5; §4.1 p.7).
- Verification / review effects: review is a gate, not a measured ablation — task "considered successfully completed only when the pull request is explicitly approved by the reviewer agent" (§4.1 p.7). No direct test of engineer-only vs engineer+reviewer; effect of review is entangled with the whole workflow. Anecdote: pre-existing/legacy test failures make strict test-driven loops pull the engineer off-task (§3.5 p.6, §5.1 p.8-9).
- Cost / tokens / latency: no cost/latency tables. Explicit context-control mechanisms: shell outputs >50k tokens auto-redirected to files (§3.2 p.5), automatic context summarization at a fixed budget (§3.6 p.7). Reviewer/PR workflow degraded when GitHub API metadata inflated context (§3.4 p.6) — context hygiene treated as first-class.
- Failure modes observed (all from §5, pp.8-10): (1) legacy/dependency/CI drift consuming the trajectory ("deprecated actions/cache v2" example) — agents burned context fixing environment instead of the issue; (2) coordination stalls — "the manager agent waited for actions from other agents that had already completed their work"; fixed by explicit completion/ready signals + reinforced `manage` semantics ("clear communication contracts are essential"); (3) conversational behaviors incompatible with automation (agents asking approval, producing plans and waiting) — fixed by automation-first prompts + `finish`/`send_message` tool separation; (4) over-engineering vs SWE-bench's minimal gold patches (functionally correct patches failed grading); (5) long test suites hitting tool time limits; (6) infra: OOM when too many parallel task teams ran on one machine. Also: execution allowed to resume from persisted GitHub artifacts after infra interruptions (benchmark-setup caveat, §5 p.8).

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: (INFERENCE) Supports the field-marshal→general→soldier shape: one non-coding manager with explicit method + per-role workers with isolated sandboxes and role-scoped tools reproduces a 72.2% SWE-bench system; the strongest borrow is "manager never edits code, worker completion must be signaled explicitly."
- Depth-2 design: (INFERENCE) No direct depth-2 evidence here; Agyn deliberately flattens communication to a single hub for traceability, which suggests depth-2 sub-orchestrators should keep the same discipline (one coordination point per sub-team, no peer-to-peer chatter) — consistent with the user's "one waiter / ack every delivery" rules.
- Which agent/model type goes in which seat: (INFERENCE) Manager + researcher on the strongest reasoning model (GPT-5-class), engineer/reviewer on a code-specialized cheaper model, matches the user's routing (Sol for coordination/deep research; Flash for routine implementation; Sonnet/Opus for review). Note reviewer here ran on the cheap code model, not a stronger model — for security-sensitive or high-risk review, the user's Sonnet/Opus-review instinct is a deliberate upgrade over this paper's setup.
- Acceptance gate: (INFERENCE) Make "reviewer/verifier approves" (not "worker says done") the definition of task complete — directly analogous to the user's reviewer audits and STATUS gates.
- Context hygiene: (INFERENCE) Redirect huge tool outputs to files and summarize context at a budget — analogous to user's worker specs + "context rotation" handoff files; the paper's manager stall anecdote validates "ack every delivery / observed turn start" rules.

## Validity
- Evidence grade: C (production case study; single benchmark run; not budget-matched; no ablation of roles/review; no repeats/error bars).
- Threats (contamination, not budget-matched, toy tasks, single model family, ...): single GPT-5 family (findings may not transfer); post hoc evaluation of a production system with resumption-from-intermediate-state allowed after infra failures (§5 p.8) — the 72.2% is not a clean controlled number; benchmark itself dated, agents spent budget on legacy CI drift; no cost or latency accounting; reviewer model = engineer model (reviewers may rubber-stamp same-model patches — same-model-family self-review bias); authors have a platform (agyn) to promote (open-source platform contribution). The 70-75% cluster elsewhere on SWE-bench 500 means the marginal advantage is within run-to-run noise, as authors themselves warn.
