## Setup
- Tasks / benchmarks (coding? repo-level? research? planning?): Full-stack software engineering (backend APIs, frontend UI, infrastructure, testing, docs) — 4 benchmark tasks (SaaS, e-commerce, real-time chat, data/platform tooling) + synthetic DAG scheduling benchmarks (task counts 20-100, depth 1-5) + a longitudinal deployment across 17 repositories. Not SWE-bench; greenfield/epic-based development.
- Models used (per role): Three-tier hierarchy: Workers = Opus (task execution); Reviewers = Sonnet (QA scoring against 10 code metrics); Investigators = Haiku (build-failure triage). Paper positions tiers as abstract capability mapping (Table 2: any provider's top/mid/cheap tiers). Replication with open-weights Qwen3.6-35B-A3B (llama.cpp, 2 slots).
- Baselines (single agent? flat team? budget-matched? yes/no + how): Controlled benchmarks: baseline = Claude Code producing a plan with its default reasoning (Experiments 2-4), No-Validation and Code-Validation-Only regimes (Exp 3), Auto-SPOQ (Exp 4); Experiment 1 compares Sequential / FIFO queue / role-based sequential pipeline / SPOQ wave dispatch on identical DAGs (10 runs each). Same model family and environment across conditions; no matched control for the field study (authors say explicitly it is not causal evidence).

## Topology tested
- Depth: 1 — orchestrator dispatches waves; three specialist tiers (worker/reviewer/investigator) but no sub-orchestrators. Orchestration vs execution is explicitly separated ("orchestration and execution are separable concerns", §2.6).
- Width (workers per orchestrator) and how it was varied: width = wave width, i.e., tasks with no mutual dependencies; varied by DAG shape (20-task fully parallel = wave of 20 down to sequential chains) and constrained in practice by hardware slots (2 on the Qwen backend) and by runtime slot-capping of the dispatcher (unbounded dispatcher regresses bimodally; capping to slot count fixes it, §6.3).
- Roles (planner, implementer, verifier, reviewer, integrator, router, ...): Human+AI epic planning (human drafts, LLM assists); planning validation gate (10 metrics); Opus workers per task; Sonnet reviewers per completed task (10 code metrics); Haiku investigators on build failure after a wave; human as consultation seat (HaaA, bidirectional). Filesystem protocol: epics/tasks as YAML in spoq/epics/active/ → complete/ on full validation; ROADMAP.md registry; journal entries with confidence scores (0-1).
- Communication / handoff format; who can write code/files: Task spec = YAML with id, deps, files_to_touch (allowed files), acceptance_criteria, PERT (o,r,p) estimates, phase (wave). Workers receive task spec + epic context + completed dependency outputs + prior QA feedback on rework. Reviewers return ≤20-line remediation feedback with file:line refs. Only workers write code; reviewer/investigator seats are read/verdict only. Validation cascade: any task scoring <95 caps epic aggregate at 85 ⇒ FAIL (no carrying weak tasks on strong averages).

## Findings (quote numbers with table/figure/page refs)
- Depth: Wave dispatch approaches the critical-path lower bound on unbounded synthetic DAGs: CP ratio 1.026-1.112 across 5 configurations, speedups 14.31× (fully parallel 20-task) down to 3.25× (depth 5); larger graphs: 6.27× (50-task) and 9.33× (100-task) (Table 5, p.19). Need for an orchestrator with explicit waves is visible: sequential, FIFO-dependency-queue, and role-based-pipeline baselines are "nearly identical" because all serialize execution (Fig 4, p.19). On the hardware-bounded backend (2 slots, real LLM calls): stable 1.4× speedup across all DAG families, matching the concurrency ceiling; ≈1.4 not 2.0× due to per-call scheduling overhead (Table 6, §6.3, pp.20-21).
- Width: Width is bounded by (a) DAG structure and (b) backend slots — capping the dispatcher to slot count is required; an unbounded dispatcher "overcommits the slot pool" and oscillates between 2-slot and sequential runtimes (§6.3, p.21). Field deployments report 1.3-5.3× wall-clock gains (§8.1; Case 1: 12 parallel components, 5.3×; Case 2: depth-limited to 5 concurrent, 2.8× — 12 tasks completed, 174 tests, zero defects, 3 orchestrator interventions for test-fixture invalidation from parallel edits, §6.7.1).
- Role → model placement: Three-tier routing is a stated design principle (Design Principle 3.5): Opus workers / Sonnet reviewers / Haiku investigators; "reserving Opus tokens for task execution while routing validation and triage through Sonnet and Haiku preserves the most expensive budget for work that demands it" (§6.7.4, p.29). No ablation of the tier mapping (not an experimental result — the paper's routing claims are design rationale, not measured). Cross-provider replication confirms orchestration gains are not model-specific (§6.3-6.6).
- Verification / review effects: Dual validation gates: planning validation (10 metrics, mean ≥95 AND min ≥90) + code validation (10 metrics, mean ≥95 AND min ≥80; includes test pass rate, requirements fidelity, OWASP security, no-TODO completeness). Ablation (Table 8, p.24): defects per task 0.34 → 0.29 (code-only) → 0.20 (full SPOQ); test pass 91.25% → 95.00% → 99.75%; static warnings 4.25 → 2.50 → 0.00; rework cycles 3.75 → 1.75 → 1.00; security issues IDENTIFIED rises 1.75 → 3.75 → 4.75 (authors interpret as broader detection, p.24). Human-assisted planning (Table 10, p.26): defects 0.47 → 0.03 per task, pass 96.50% → 99.75%, at the cost of more rework (1.00 → 2.50 cycles) and far more LOC churn (5.75 → 104.25) — "HaaA ... does not minimize effort; it makes that effort more effective." Plan quality (Table 7, p.21): SPOQ coverage 93.0→99.75, dep errors 3.75→1.25, cyclic plans 3/4→0/4, parallelism potential 31.0→75.25, granularity 66.0→91.0 (Claude); Qwen baseline is rescued (coverage 56.2→91.2) — structured planning is "more load-bearing for smaller models" (§6.4, p.22).
- Cost / tokens / latency: ~$1.95 per Opus worker task (25K in/5K out) ≈ $28 per 13-task epic; flat-rate Max plan ≈ $0.10/task at scale (20× reduction) (§6.7.4, p.29). Field: 19 combined tasks planned+executed in a 3-hour session with 6 concurrent Claude Code instances under one Max license (~6 tasks/hour) (§6.7.2, p.29). Deployment totals: 17 repos, 8,589 commits, 1,822 completed tasks, 183 epics, 1,687 journal entries; 13,866 tests run with 99.87% pass (13,848/13,866) across 591 suites (§6.7.2, p.28).
- Failure modes observed (9 operational risk categories, §6.7.3 p.29 + Appendix B.5, pp.47-50): (1) resource contention — concurrent `npm install` lock-file conflicts (EBUSY; 12-min debugging), build-directory corruption (.next/dist); mitigation = single Wave-0 dependency-install task, sequential builds between waves; (2) context exhaustion — 180K-token agent hallucinating function signatures; mitigation = self-contained tasks, files_to_touch scope limits, 20-line feedback limit, context-budget alerts at 70%; (3) runaway loops — one agent executed `npm install sonner` >100 times, ~$15 burned before detection; mitigation = halt on 5+ repeated identical commands, 30-min task time limits; (4) validation gaming — tests asserting true===true, short-circuited edge cases; mitigation = complementary metrics + human review + mutation testing + cross-validation by independent agents; (5) coordination conflicts — duplicate utility functions with different signatures, agents assuming tables/state still being created, conflicting CSS classes; mitigation = wave boundaries as sync points, explicit interface contracts, post-wave merge verification; (6) cost runaways (>$100/hr extrapolated with 10+ agents); (7) human consultation latency stalling wave progression; (8) execution isolation/security (hallucinated rm -rf, no sandboxing in reference impl); (9) rollback/recovery gaps (no automatic rollback — git checkpoints at wave boundaries recommended). Test files treated as "implicit dependents of the components they exercise" after fixture-sync failures (§6.7.1).

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: (INFERENCE) SPOQ is the closest published analogue of the user's operating model (plan → validate → dispatch → validate; explicit task files with owned files + acceptance criteria; STATUS/journal). Its controlled numbers are weak-to-moderate (4 tasks, single-author field study) but its protocol details are worth borrowing wholesale: (a) wave assignment = the user's "staged hand-offs"; (b) validation cascade (any weak task caps the epic) = the user's STATUS gates done right; (c) ≤20-line remediation feedback = anti-context-bloat for handoffs; (d) halt-on-repeated-command + per-task budgets = concrete guards against the user's observed "workers stuck" and quota-limit issues.
- Depth-2 design: (INFERENCE) Two-level orchestration should preserve wave semantics at each level: a sub-orchestrator's workers within one wave, waves between sub-teams synchronized at boundaries (git checkpoint between waves; the user's sole-integrator merges at wave boundaries, not continuously). The 5+ repeated-command halt and validation cascade should be enforced recursively by sub-orchestrators, since runaway costs compound per agent (their citation: one runaway ≈ $15; 10+ agents > $100/hr).
- Which agent/model type goes in which seat: (INFERENCE) Directly mirrors and (design-)justifies the user's routing: top model for implementers (this paper: Opus workers), mid model for review (Sonnet), cheapest for triage/investigation (Haiku); planner is human+strong model. Caveat: SPOQ's tier assignment is rationale, not an experiment — the strongest controlled routing evidence remains SWE-Review (reviewer strength must scale with patch strength) and Agentic Rubrics (authoring rubrics needs capability; grading does not). Note SPOQ puts the STRONGEST model in the implementer seat and mid in review — the opposite of the user's Sonnet-reviewing/Gemini-implementing setup; the user's setup needs a reviewer at least as strong as the worker, which the paper does not contradict (Sonnet > Opus is not claimed; their reviewers merely review Opus work) — INFERENCE: validate the user's split per task class.
- Human seat: (INFERENCE) The user's own supervision (acks, approvals, stop procedures) is a HaaA-style seat; SPOQ quantifies its value (defects 0.47→0.03 through planning-stage human review) and prescribes the mechanism: human validates the plan, agents can block on consultation (with timeout/fallback so a busy human doesn't stall a wave — the user's "one waiter" concern).
- Applicability gate: (INFERENCE) SPOQ says orchestration overhead only pays for projects with 5+ parallelizable tasks / 4+ hours of work — supports the user's "keep fan-out minimal".

## Validity
- Evidence grade: C+ (preprint; controlled for Exp 1 (10 runs/config) but experiments 2-4 aggregate only 4 tasks with vendor-built rubrics; heavy field study lacks matched controls; authors self-disclose most limitations).
- Threats (contamination, not budget-matched, toy tasks, single model family, ...): Experiment 1 synthetic sleeps measure the scheduler, not coding; Exp 2-4 rely on LLM-scored metrics without inter-rater reliability testing (authors admit "metric reliability" limitation, p.31); security "improvement" is really detection-coverage change; baseline planning by Claude Code may understate what a well-prompted planner does; Qwen replication is single-shot per task (direction only); field study: shared development context, no control group, self-reported confidence scores; possible marketing incentives (commercial Pinpoint Technologies, productized methodology); cost estimates are approximations and exclude human time.
