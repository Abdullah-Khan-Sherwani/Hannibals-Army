## Setup
- Tasks / benchmarks: GAIA (tool-intensive assistant tasks, 165 validation questions across 3 levels), GPQA (Diamond split, 198 expert scientific reasoning questions), AIME (2024–2025, 60 mathematical competition problems), MuSiQue (200 multi-hop factual retrieval questions), HLE (Humanity's Last Exam, 200 frontier academic questions); Section 4, p. 4; Appendix A, p. 10.
- Models used (per role):
  * Orchestrators: Qwen3-8B and Qwen3-32B (evaluating planning and thinking capacity; Section 4, p. 3).
  * Sub-agents: Qwen3-1.7B, Qwen3-8B, Qwen3-32B (evaluating executor scale; Section 4, p. 3; Section 5.3, p. 5).
  * Monolithic Baselines: Qwen3-32B base (no tools) and Qwen3-32B direct single-agent with all tools attached.
- Baselines: Single-agent direct tool use (full prompt history replay) vs modular multi-agent system with structured memory, systematically ablated across thinking placement (None, Sub-agent only, Orchestrator only, All); Section 4, p. 3–4.

## Topology tested
- Depth: 1 (Decoupled hierarchical hub-and-spoke: central Orchestrator handles planning and global state, dispatching subtasks to specialized single-turn Sub-agents; Figure 1, p. 3).
- Width: Fixed 3 specialized sub-agents (Web Searcher, Coder, File Inspector; Section 3, p. 3).
- Roles: Central Orchestrator (decomposes query, selects tools, writes/reads structured memory) + Specialized Worker Sub-agents (Web Searcher, sandboxed Python Coder, File Inspector for PDF/CSV/text); Section 3, p. 3.
- Communication / handoff format; who can write code/files: Strictly boundary-only communication between Orchestrator and individual Sub-agents; sub-agents NEVER communicate with each other. Both write to a shared structured memory store (query analysis, previous steps, tool results, sub-goals), but ONLY the Orchestrator reads from it; Section 3, p. 3.

## Findings (quote numbers with table/figure/page refs)
- Depth: Depth-1 modular orchestration allows small models to match or outperform 4× larger monolithic models: an 8B multi-agent system with orchestrator-only thinking matches a 32B single agent with direct tools on GAIA (23.0 vs 23.0) and substantially beats it on AIME (55.0 vs 45.0, +10.0 pp), while tracking closely on GPQA (58.6 vs 60.1) and MuSiQue (14.0 vs 15.0; Section 5.1, p. 4–5; Table 1).
- Width: System performance is governed entirely by orchestrator planning, not worker width or worker size.
- Role → model placement:
  * Sub-agent size is negligible once Orchestrator thinking is active: On GAIA, an 8B thinking orchestrator achieves 23.0 with 1.7B sub-agents, 23.0 with 8B sub-agents, and 23.6 with 32B sub-agents (Section 5.3, p. 5–6; Figure 2). Upgrading sub-agents from 1.7B to 32B produces essentially zero gain. Under a 32B orchestrator, 8B sub-agents (21.2) actually underperform 1.7B sub-agents (22.4).
  * Multi-agent systems are planner-limited, not executor-limited: Investment in orchestrator capability and reasoning yields massive returns, whereas scaling sub-agent parameter size is wasteful (Section 5.3, p. 6).
  * Explicit reasoning (thinking) belongs ONLY in the Orchestrator:
    - Orchestrator-only thinking produces the largest system-wide improvements (+18.2 GAIA, +36.7 AIME, +10.0 MuSiQue; Section 5.1, p. 4). It halves tool execution calls (2.7 $\to$ 1.1) and reduces turns (3.6 $\to$ 2.0), adding only +0.6s latency (Section 6.1, p. 6–7; Figure 3–4).
    - Sub-agent thinking is counterproductive: It adds +77% latency (+6.1s decoding overhead vs +0.6s for orchestrator), increases tool thrashing (GAIA tool calls increase 447 $\to$ 483), and degrades accuracy (Section 5.2 & 6.2, p. 5, 7; Figure 3).
- Verification / review effects: Coder sub-agent operates as an execution verifier in sandboxed Python; however, ablations show removing the Coder slightly improves AIME (55.0 $\to$ 60.0) and GPQA (58.6 $\to$ 59.6) because code verification introduces over-deliberation and overrides correct symbolic reasoning traces (Table 2, p. 11; Section 6.3, p. 8).
- Cost / tokens / latency:
  * Structured memory cuts token accumulation by 43% relative to single-agent history replay (9.1K–11.7K tokens vs 19.5K; Section 6.1, p. 6; Figure 3).
  * 8B MAS is 4.2× faster than 32B single-agent direct execution (7.9s vs 32.9s per query; Section 6.1, p. 7).
- Failure modes observed: (1) Over-trusting tools: retrieved web content overriding correct parametric memory on scientific questions (GPQA drops -5.0 pp when unguided tools are added; Section 5.1, p. 4; Section 6.3, p. 8); (2) Over-deliberation in sub-agents: sub-agents generating lengthy internal rationalizations that confuse downstream coordination; (3) Context accumulation in direct baselines growing quadratically without structured memory summaries (Section C.2, p. 11).

## Implications for Hannibal's Army (label each as INFERENCE)
- Depth-1 design: INFERENCE: Enforce an asymmetric reasoning budget: allocate high reasoning effort (thinking traces / CoT) to the Orchestrator, but strictly disable thinking / CoT on soldier execution agents. Soldiers should execute direct, concise tool actions; giving soldiers chain-of-thought adds 77% latency and tool thrashing.
- Depth-2 design: INFERENCE: In Field Marshal → Generals → Soldiers, Generals must manage a structured memory state (compact summary records of completed sub-goals) rather than passing raw multi-turn conversation logs across tiers, which cuts token accumulation by 43%.
- Which agent/model type goes in which seat:
  * Orchestrator / Coordinator / General: Model with explicit reasoning enabled (Sonnet / GPT-6.1-Sol / Qwen-32B thinking), as planning capacity sets the entire ceiling.
  * Worker / Soldier Sub-agents: Lightweight, cheap models (1.7B–8B / Gemini Flash) without thinking traces. Scaling worker size from 1.7B to 32B produced zero accuracy gain on GAIA (flat 23.0).
  * Inter-agent Communication: Ban peer-to-peer worker messaging. Restrict all communication to strict hub-and-spoke (Orchestrator $\leftrightarrow$ Worker) to avoid coordination overhead.

## Validity
- Evidence grade: A (Peer-reviewed workshop paper at ICLR 2026; controlled factorial ablations across 5 benchmarks, 3 model sizes [1.7B, 8B, 32B], 4 thinking configurations, and hardware latency/token accounting on H100s).
- Threats: Evaluated within the Qwen3 model family; tasks limited to QA and tool benchmarks (GAIA, GPQA, AIME, MuSiQue, HLE) rather than full multi-file software repositories.
